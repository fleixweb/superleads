# Slice AH：批量客户开发内核复盘与发现候选池分区纠偏

日期：2026-07-30

## 1. 本 Slice 要解决什么

Code Slice AF 已把三条入口路由收稳，Code Slice AG 已把单一客户背调补成独立工程路线。现在最需要校准的是第一条路线：**批量客户开发**。

本轮最重要的新事实不是“缺一个中间档”，而是：`初筛客户名单` 目前不是安全的待实现枚举，而是一个会绕过默认发现候选池纪律的活口。

当前代码中，`scripts/validate_research_graph.py` 的默认发现 Candidate 结构检查只在 `brief.output_mode == "发现候选池"` 时执行。只要 Brief 写成 `初筛客户名单`，去重依据、业务相关性依据、五类公开信号状态、`unknowns`、`source_restrictions` 等候选池纪律就可能被静默跳过；后续 audit / bulk Markdown 仍会按 `initial_lead_list` 渲染成“发现候选池”。

因此，本 Slice AH 纠偏后的核心结论是：

> 批量客户开发不新增独立 L2“初筛客户名单”层级。默认弱证据交付仍是“发现候选池”。所谓初筛价值，应在发现候选池内部通过分区、依据状态、联系方式状态、搜索覆盖和待确认项表达；`初筛客户名单` output_mode 应在后续 Code Slice AH 中显式拒绝或映射回发现候选池纪律，不能成为绕过口。

本 Slice 只做产品内核复盘和文档纠偏，不写代码、不联网采集客户、不生成名单。

---

## 2. 批量客户开发的一句话定义

批量客户开发是：

```text
用户当前卖什么 + 本次想找哪类海外客户 -> 发现候选池；用户明确要求并接受严格核验成本时 -> 标准开发名单
```

它服务的真实外贸动作是：

- 找到一批可能相关的海外公司；
- 看清这些公司为什么被列入；
- 看清哪些公开信号已经看到、哪些没查、哪些来源受限；
- 看清公开联系方式是否可用、是否需要核实归属；
- 把明显不符合、本次仅作参考、主体冲突的对象保留下来给用户判断；
- 让销售可以继续人工跟进、补证或二次筛选。

它不是：

- 自动推荐客户；
- 采购概率预测；
- 商业价值排序；
- 市场进入建议；
- 单一客户背调；
- 产品出海市场准入分析；
- 默认严格审计或完整核查版。

## 3. 三条路线边界再校准

| 用户真实意图 | 应走路线 | 批量客户开发里怎么处理 |
|---|---|---|
| “帮我找美国柴油发电机配件经销商” | 批量客户开发 | 找发现候选池，展示业务信号、联系方式、来源状态和待确认项 |
| “开发中东市场，找汽车配件经销商” | 批量客户开发 | `开发市场` 在这里是找客户语义，不应误路由为产品市场分析 |
| “找需要 UL/CE 认证产品的进口商” | 批量客户开发 | 认证词是客户属性或筛选线索，不是问目标国法规要求 |
| “这个锂电池出口美国要不要 UN38.3 / SDS / COO / 关税多少” | 产品出海市场分析 | 不生成客户名单；先查产品进入目标国条件 |
| “帮我查一下 example.com 靠不靠谱” | 单一客户背调 | 只背调一个指定对象，不扩展客户池 |
| “先分析产品进入美国，再找客户” | 先产品出海市场分析，后续另启批量客户开发 | 不把市场分析中的渠道或价格自动变成客户范围 |

批量客户开发的范围必须来自**当前用户原话和当前 Brief**，不能从其它路线、旧运行、行业默认、产品市场分析结论中自动继承。

## 4. 真实外贸业务中的客户类型是开放文本，不是固定枚举

批量开发中，目标客户类型应保留用户表达，而不是锁死在枚举里。真实外贸里可能出现：

| 类型 | 例子 | 处理原则 |
|---|---|---|
| 进口商 / distributor / dealer | 进口商、区域经销、品牌代理 | 可作为目标客户角色，但仍需公开业务信号支持 |
| 批发商 / wholesaler | B2B 批发、批发目录、渠道商 | wholesale 入口只证明沟通入口，不证明采购意愿 |
| 零售商 / 连锁 / 专卖 | 零售连锁、建材店、汽配店、户外店 | 零售属性不等于采购中国货，需要产品/渠道信号 |
| 服务商 / 维修商 / 安装商 | 维修服务、工程安装、售后服务 | 很多后市场产品真实客户不是进口商，而是服务/备件渠道 |
| 项目 / 工程 / 承包商 | EPC、工程公司、酒店用品项目、政府项目供应商 | 项目角色可作为线索，不能写成采购预算或中标可能 |
| 品牌商 / 私牌商 / OEM 客户 | Private label、brand owner、OEM buyer | 只有用户允许时纳入；不能默认把品牌商当客户 |
| 电商 / 平台卖家 | Amazon seller、独立站、平台店铺 | 可作为公开价格和渠道线索，也可在用户明确时作为客户类型 |
| 制造商 / 同行 / 原厂 | OEM、品牌原厂、同类制造商 | 默认仅作参考或排除，除非用户明确允许找同行/OEM 采购方 |
| 贸易公司 / sourcing office | trading、buying office | 可作为客户或中间商，但需要当前任务允许 |

原则：

1. 客户类型是自由文本合同，不是静态 ICP。
2. 同一词在不同行业可能含义不同，例如 dealer 可能是整机经销、配件渠道、维修网络或授权服务商。
3. 用户没有说的国家、产品应用、公司规模、渠道和客户角色不能自动补。
4. 竞争对手、品牌、制造商、种子网站默认是搜索参考，不自动成为可开发客户。

## 5. 批量客户开发交付层级：不新增“初筛客户名单”层

### 5.1 纠偏后的层级

| 层级 | 用户可见名称 | 何时使用 | 证据门槛 | 不能说成什么 |
|---|---|---|---|---|
| L0 | 方向样本 | 用户方向仍有关键歧义；不同答案会导致客户方向相反 | 1-5 个样本，作为发现候选池内注记 | 正式客户、推荐客户、已验证客户 |
| L1 | 发现候选池 | 默认批量客户开发交付 | Candidate + 当前 Run/Brief/Plan 绑定 + 发现来源/搜索记录/来源提示 + 去重依据 + 业务相关性 + 五类公开信号状态 + unknowns/source_restrictions | 标准开发名单、高质量客户名单、推荐客户 |
| L2 | 标准开发名单 | 用户明确要求正式核查 / 联系人归属核验 / 标准开发名单 | Entity + Source/Observation + Claim/ClaimEvidence + ScopeDecision + Assessment + Review/Audit | 采购概率、成交预测、商业价值排序 |
| 不提供 | 完整核查版 | 当前本地部署不提供 | 不可交付 | 不得伪装成可用模式 |

`初筛客户名单` 不再作为独立层级。它在 schema 中存在，但当前不是实现完备的安全交付模式。后续 Code Slice AH 应优先把它显式拒绝、禁用，或强制映射回 `发现候选池` 的完整候选结构检查，而不是新增第 6 个 output_mode / exporter mode / delivery_status。

### 5.2 为什么“中间状态”仍然需要表达，但不需要新层级

真实外贸业务里，大量有用客户处在“完全未核实”和“正式标准名单”之间：

- 官网打开了，能看到产品/应用/渠道信号，但没有完整联系人归属；
- 多个公开弱来源指向同一业务方向，但未形成正式 Claim；
- 目录、展会、B2B 页面、官网栏目、PDF 片段可以说明“可能相关”，但不能证明采购需求；
- 联系入口公开可见，但不能确认具体采购负责人；
- 公司主体基本清楚，但品牌、分支、经销关系还要人工确认。

这些中间状态不应被删除，也不能升级为正式客户。正确做法不是新增“初筛客户名单”，而是在**发现候选池内部**分区展示：

```text
发现候选池
├─ 可优先人工跟进：直接相关 / 可能相关，且有可展示依据
├─ 待确认：主体待确认 / 信息不足 / 来源受限 / 说法冲突
└─ 已排除 / 仅作参考：明确不符合、竞争品牌、原厂、参考对象
```

这三分区是视图和展示方式，不是新的 delivery_status，也不是新的 output_mode。

## 6. 发现候选池的对象和证据边界

### 6.1 L1：发现候选池是默认弱证据交付层

发现候选池可以只由 Candidate 层支撑。最低字段：

- 公司名或线索名；
- 当前 Run / Brief / Plan 绑定；
- 发现来源：`source_hint` / 安全公开 `source_url` / `discovery_refs` / SearchLog 结果引用；
- 去重依据；
- 业务相关性状态；
- 业务相关性依据；
- 五类公开信号状态；
- 未知项；
- 来源受限；
- 下一步待核查。

发现候选池允许弱线索，但必须标清：

| 情况 | 正确表述 |
|---|---|
| 搜索结果出现目标关键词 | 可作为发现线索，不写成已观察业务事实 |
| 官网未打开 | 来源状态写来源受限或未打开，不写“已确认相关” |
| 只有目录名或展会名 | 信息不足或可能相关，保留待确认 |
| 同名公司 / 域名冲突 | 主体待确认，不拼接联系方式和业务信号 |
| 多来源弱信号方向一致 | 多来源方向一致，不写已验证客户 |
| 联系入口公开可见 | 联系入口，不等于采购意愿或采购负责人 |

发现候选池不要求：

- 完整 Entity 解析；
- Claim / ClaimEvidence；
- ScopeDecision；
- Assessment；
- 独立 ReviewAttestation；
- DeliveryManifest。

这些不是 L2 新规则，而是默认发现本来就应遵守的弱证据规则。

### 6.2 L2：标准开发名单只在显式正式核查时启用

标准开发名单继续保留严格门禁，但只能在用户明确要求时启用。

标准开发名单的存在理由：

- 用户要的是可进入 CRM 或销售任务的更稳名单；
- 用户要求联系人归属核验；
- 用户要求正式标准开发名单；
- 用户愿意接受更低产量、更高核验成本。

即使通过正式链路，也只代表“符合本次方向且来源链条可复核”，不代表会采购、值得开发或成交概率高。

## 7. 批量客户开发的用户可见状态

批量客户开发应分开两类状态：

### 7.1 业务相关性状态

继续使用五类业务相关性，但用户端要说人话：

| 内部状态 | 用户可见表达 | 含义 |
|---|---|---|
| `directly_related` | 直接相关 | 已观察到与本次产品、应用、客户角色、渠道或地域相符的公开信号 |
| `possibly_related` | 可能相关 | 有产品线、目录、行业、渠道或地域线索，但还不能确认具体业务关系 |
| `identity_pending` | 主体待确认 | 名称、域名、地址、贸易记录或联系方式无法安全归到同一主体 |
| `insufficient_information` | 信息不足 | 目前只有弱线索，不能确认相关性 |
| `explicitly_excluded_or_unrelated` | 已排除 / 不符合 | 已观察到命中排除边界或明显不相关 |

这些状态不是采购意愿、客户质量或价值排序。

### 7.2 依据状态应回到发现候选池主表

批量客户开发主表需要新增“依据状态”列，复用 Slice AE 的用户可见状态词子集。这是发现候选池展示缺口，不是新增 `初筛客户名单` 层级的理由。

| 依据状态 | 在批量客户开发中的含义 |
|---|---|
| 已有明确依据 | 已打开来源本身支持当前字段，例如官网展示目标产品/应用/服务入口 |
| 多来源方向一致 | 多个独立弱来源指向同一客户方向，但不等于正式核查 |
| 可作为线索 | 搜索结果、目录、展会、平台页或未充分打开来源提供了可跟进方向 |
| 需补充资料 | 需要用户提供目标客户边界、排除项、产品适配或已有名单 |
| 需权威/专业复核 | 涉及资质、注册、进口记录、代理关系、商标关系等需专业/权威来源核实 |
| 资料过旧需复核 | 公开资料日期较旧或未知，不能当作当前经营状态 |
| 来源受限 | 登录墙、付费墙、403、JS 空壳、摘要页或工具无法打开 |
| 说法冲突待复核 | 来源之间主体、地区、业务或联系方式冲突 |
| 本轮未执行 | 某类搜索或联系入口采集未执行 |
| 暂不适用 | 当前 Brief 未要求该类信号，例如不查贸易记录或不查 LinkedIn |
| 按已知数据计算 | 批量客户开发中少用；如出现统计汇总，只能说明计算口径 |

当前实现中，11 个状态词检查主要落在产品出海市场分析路线；bulk Markdown 主表尚未稳定显示“依据状态”。这是后续 Code Slice AH 应修的用户可见缺口。

## 8. 批量客户开发的默认报告结构

### 8.1 开场四行

| 字段 | 要说什么 |
|---|---|
| 我理解你卖的是 | 保留用户自己的产品/服务表达，不自动改写为行业词 |
| 本次优先找 | 国家/地区、客户类型、渠道、应用、关键词等当前 Brief 范围 |
| 本次不纳入 | 用户明确排除项；未明确时说明同行/原厂/参考品牌不自动当客户 |
| 判断依据将重点看 | 公开业务信号、产品/应用匹配、主体归属、联系方式来源、未覆盖路径 |

### 8.2 发现候选池主表：单表三分区

建议字段：

| 字段 | 人话解释 |
|---|---|
| 分区 | 可优先人工跟进 / 待确认 / 已排除或仅作参考 |
| 候选客户 | 公司名、品牌名或线索名 |
| 国家/地区 | 公开来源或用户条件中的地区；不猜注册地或经营地 |
| 可能客户角色 | 经销商、批发商、维修商、零售连锁、项目商等自由文本；无依据不猜 |
| 当前看到的业务信号 | 已看到什么，或为什么只是线索 |
| 业务相关性 | 直接相关 / 可能相关 / 主体待确认 / 信息不足 / 已排除 |
| 依据状态 | 已有明确依据 / 多来源方向一致 / 可作为线索 / 来源受限 / 说法冲突待复核等 |
| 可用联系入口 | 邮箱、电话、表单、社媒入口及其状态；主表可放摘要 |
| 还要确认什么 | 产品适配、采购模式、地区覆盖、是否接受外部供应商、联系人归属等 |
| 来源 / 来源状态 | 来源名称、链接或来源限制 |

### 8.3 联系方式汇总

联系方式要分三态：

| 状态 | 用户端表达 | 使用边界 |
|---|---|---|
| `ready` | 可直接使用 | 来源与主体归属明确；仍不等于采购意愿 |
| `export_with_source_note` | 建议核查后使用 | 公开可见，但归属、时效或用途需确认 |
| `needs_manual_association_review` | 待确认归属 | 有价值线索，但不能安全绑定主体 |

禁止导出猜测邮箱、无来源联系方式、跨主体错配联系方式、用户材料中应隐藏或 hold 的联系方式。

### 8.4 搜索覆盖与收敛

用户应看到的是业务覆盖，不是内部 SearchLog 对象名：

- 本轮查了哪些方向；
- 哪些国家/语言/来源类型覆盖过；
- 哪些路径新增候选较多；
- 哪些路径主要重复或无关；
- 哪些来源受限或未执行；
- 是否达到“本轮发现收敛”。

“收敛”只表示本轮查询组合下新增候选明显减少，不表示找全了全网客户。

### 8.5 已排除 / 仅作参考

明确排除项和参考对象不能静默删除。应单独展示：

| 类型 | 展示方式 |
|---|---|
| 用户明确排除客户 | 已排除客户 |
| 原厂 / 同行 / 竞争品牌 | 默认仅作参考，除非用户允许 |
| 不在目标地区或错误应用 | 已排除 / 不符合 |
| 主体冲突 | 主体待确认，不合并、不删除 |

### 8.6 当前 bulk Markdown 的真实缺口

当前 `export_workbook.py --mode initial` 已能输出 7 张表：

```text
发现候选池、联系方式汇总、官网与来源链接、搜索覆盖与收敛、待核查事项、已排除客户、风险与说明
```

但 `export_superleads_markdown.py` 的 bulk 路线目前只渲染开发方向、发现候选池样表、待确认事项、信息来源四块，缺少：

- 联系方式汇总；
- 搜索覆盖与收敛；
- 已排除 / 仅作参考；
- 依据状态列；
- 发现候选池三分区。

这些是后续 Code Slice AH 的核心施工项。它们都属于发现候选池展示优化，不需要新增 `初筛客户名单`。

## 9. 多来源互证在批量客户开发中的用法

批量客户开发需要表达“线索收敛”，但不能把它当作正式验证。

| 多来源情况 | 用户可见表达 | 禁止升级 |
|---|---|---|
| 官网 + 展会目录都显示目标产品方向 | 多来源方向一致 | 不等于已确认采购需求 |
| B2B 平台 + 公司目录 + 地图都显示相同业务 | 多来源方向一致，可人工复核 | 不等于推荐客户或高质量客户 |
| 多个页面来自同一域名 | 同一来源多页面 | 不能算独立互证 |
| 搜索摘要 + 未打开页面 | 可作为线索 | 不能算已观察业务信号 |
| 用户旧名单 + 公开官网一致 | 用户材料与公开来源方向一致 | 用户材料不是外部事实本身 |

未来 Code Slice AH 可新增 Candidate 级 `corroboration_summary` 或复用已有互证思想，但第一原则是：**多弱来源只提升线索可读性，不升级为正式事实。**

Code Slice AH 不应实现独立 `初筛客户名单`，而应先修绕过口，再优化发现候选池展示。

## 13. 用户可见文案冻结

批量客户开发报告顶部必须保留这类说明：

```text
本次输出是发现候选池，不是正式开发名单。
公开联系入口不等于采购意愿；公开职位不等于采购负责人。
弱线索会保留并标注状态，是否继续开发由用户自行判断。
```

禁止在发现候选池里写：

```text
推荐客户
高质量客户
重点开发
采购概率
成交概率
已确认采购需求
采购负责人已确认
建议优先开发
最值得开发
```

如未来保留标准开发名单中的 `开发建议` 工作表，也应改成人工跟进动作或资料核验建议，而不是客户价值排序。

## 14. 非目标

本 Slice AH 不做：

- 不联网找真实客户；
- 不生成任何新客户名单；
- 不修改 schema、validator、exporter 或 eval；
- 不删除现有正式名单链路；
- 不引入国家、行业、客户类型硬编码库；
- 不把产品市场分析里的渠道或价格结论继承为客户开发范围；
- 不把 `初筛客户名单` 包装成新的可交付层级。

---

## 15. 决策

从 Slice AH 起，批量客户开发的产品心智冻结为：

1. 默认弱证据交付是发现候选池；
2. 不新增独立 `初筛客户名单` 层级，不新增 delivery_status / exporter mode / audit 分支；
3. `初筛客户名单` 作为当前 schema 中的危险枚举，后续 Code Slice AH 必须显式拒绝、禁用或强制回落到发现候选池纪律；
4. 发现候选池内部用“可优先人工跟进 / 待确认 / 已排除或仅作参考”三分区表达中间状态；
5. 发现候选池主表需要增加“依据状态”，并补齐联系方式汇总、搜索覆盖与收敛、已排除 / 仅作参考等 Markdown 展示缺口；
6. 标准开发名单只在用户明确要求正式核查时启用；
7. 多来源一致、联系入口、目录出现、平台页面、贸易线索都只能增加“可跟进性”，不能变成采购意愿、推荐客户或采购概率；
8. 所有用户可见表格都应说外贸人话：看到什么、从哪来、能当什么、不能推出什么、下一步人工确认什么。
