# Slice T：三条路线用户交付标准冻结

日期：2026-07-27

## 1. 本 Slice 要解决什么

Slice S 已经用三个真实外贸任务跑出用户可见样本，但它仍然是人工验收。Slice T 的目标是把这三份样本沉淀为稳定输出合同和静态 eval，防止后续改代码时把 Superleads 再次改成内部工作流语言。

本 Slice 不新增真实搜索、不补新来源、不扩展事实结论；只锁定用户最终看到的表达形态。

## 2. 三条路线的交付对象

| 路线 | 用户真正要的东西 | 用户可见主交付 | 不能变成什么 |
|---|---|---|---|
| 批量客户开发 | 找一批可继续核查和跟进的海外候选客户 | 候选客户池样表 | 推荐客户排序、采购概率、正式标准名单 |
| 单一客户背调 | 查清一个指定公司/品牌/域名是谁、做什么、怎么联系 | 表格化客户背调报告 | 批量客户开发、采购意愿断言、负责人猜测 |
| 产品出海市场分析 | 查一个产品进入目标国家/地区的客观市场与准入条件 | 市场与准入信息矩阵 | 客户名单、市场进入建议、推荐报价、最终税费结论 |

## 3. 共同用户可见规则

| 规则 | 必须做到 | 不允许 |
|---|---|---|
| 人话字段 | 用“已看到什么 / 状态 / 还要确认什么 / 不能推出什么” | 暴露 `graph`、`EvidenceCard`、`SearchLog`、`Claim`、`MatrixRow`、`rule id`、`eval` 等内部语言 |
| 表格优先 | Markdown 表格或 CSV 表头能直接给业务人员看 | 大段散文堆砌 |
| 弱证据保留 | 线索、候选、待确认、未执行、来源受限都显示出来 | 因证据弱就静默删除，或为了好看写成确定结论 |
| 不做价值主张 | 只列客观信号、限制和下一步核验项 | “值得进入”“建议开发”“推荐客户”“最佳路线”“推荐报价” |
| 来源边界 | 来源、观察日期、来源状态、待复核范围尽量可见 | 搜索摘要、外部模型摘要、平台价、网页标签、证书入口直接升级成事实 |

## 4. 批量客户开发输出合同

### 4.1 开场四行

批量客户开发必须先用四行说清方向：

| 字段 | 说明 |
|---|---|
| 我理解你卖的是 | 复述用户产品，不额外发明品类 |
| 本次优先找 | 复述用户指定国家、客户类型、渠道或应用 |
| 本次不纳入 | 复述用户排除边界，未明确则不强行添加 |
| 判断依据将重点看 | 说明将看哪些公开业务信号 |

### 4.2 候选客户池表

最小表头：

| 表头 | 用途 |
|---|---|
| 候选客户 | 公司/品牌/网站名称 |
| 当前看到的业务信号 | 已看到或待核查的公开业务线索 |
| 相关性状态 | 直接相关、可能相关、边界线索、信息不足、身份待确认、已排除 |
| 可用联系入口 | 官网、表单、公开邮箱/电话；不猜邮箱 |
| 还要确认什么 | 采购角色、产品适配、区域、是否接受供应商等 |
| 来源 / 来源状态 | 已打开公开来源、公开入口待复核、来源受限等 |

### 4.3 批量客户开发禁止项

- 不写“推荐客户”“最佳客户”“采购概率”。
- 不把公开 contact / quote / wholesale 入口写成采购意愿。
- 不把同行制造商、OEM、参考品牌默认纳入，除非用户明确允许。
- 不因来源打不开就写“不相关”或删除候选。

## 5. 单一客户背调输出合同

### 5.1 必须先锁定对象

报告只围绕用户指定的公司、品牌、域名、地址、邮箱或材料锚点，不顺手扩成一批新客户。

### 5.2 推荐表格结构

| 表格 | 解决的问题 |
|---|---|
| 一句话先说清 | 先告诉用户当前对象大概是谁，哪些不能证明 |
| 客户一眼看懂 | 主体、产品、B2B 入口、采购需求、负责人边界 |
| 客户、品牌与关联方 | 品牌、注册主体、母公司/运营方/人员线索分开 |
| 公开业务信号与可沟通角度 | 只列公开看到的业务信号和可询问方向 |
| 怎么联系、先找谁 | 公开入口、为什么用、先问什么、状态 |
| 跟进前要注意什么 | 采购意愿未知、联系人角色未知、第三方来源受限等 |
| 信息从哪里来 | 来源、位置、观察日期、状态 |

### 5.3 单客背调禁止项

- 不把董事、Founder、Owner 默认写成采购负责人。
- 不把 wholesale / co-brand / contact 入口写成采购意愿。
- 不把 Similarweb、海关、社媒或第三方受限页面写成已核实流量/采购量。
- 不自动生成同类客户名单。

## 6. 产品出海市场分析输出合同

### 6.1 顶部先看贸易前提

产品市场分析必须先把贸易地理角色分开：

| 字段 | 说明 |
|---|---|
| 产品 | 产品名、型号、版本 |
| 目标销售国家/地区 | 用户要进入或销售的国家/地区 |
| 出口申报国 | 可默认中国，但必须可改；用户未确认时写待确认 |
| 原产国 / 制造来源 | 公开来源、用户材料或贸易文件支持的原产/制造线索 |
| 实际起运地 / 起运港 | 未公开时写待确认，不能猜港 |
| 目的节点 | 港口、机场、仓库、项目地；未知则待确认 |

### 6.2 必须覆盖的业务模块

| 模块 | 最小要求 |
|---|---|
| 产品档案与触发项 | 材质、用途、规格、带电/带电池、磁性、液体、粉末、化学/危险品、食品接触、皮肤接触、儿童用品、农产品、冷链、散杂/RoRo/大件等 |
| 长期需求与搜索趋势 | Google Trends 只能写相对搜索兴趣，不等于销量；未执行要明示 |
| 公开市场资料与行业信息 | 只引用已打开或用户提供可复核来源；报告摘要不成事实 |
| 线上市场与价格参考 | 平台价只能作为挂牌价/参考价，不变成交价、批发价、推荐报价 |
| 季节、节日与销售窗口 | 礼品属性、节假日、淡旺季必须有来源；未执行要明示 |
| 产品准入与合规要求 | 认证、包装、质量、标签、危险品、检验检疫、两用物项等按触发项核验 |
| 进口税费 | HS/HTS 只能候选；最终税率和税额需报关日、实物归类、原产地、附加税项 |
| 原产地证明 / COO | 先判断目标国规则是否需要，再单独显示用户材料是否已准备 |
| 出口国要求 | 出口申报国的商检、认证、检验检疫、出口管制等 |
| 运输方式与申报节点 | 海运整柜、拼箱、散杂、RoRo、铁路、陆运、空运、快递按货物属性条件化列出；只写常见区间，不写承诺交期 |
| 近期外部因素 | 政治、战争、自然灾害、金融、假期、港口拥堵等必须有日期和来源 |
| 信息来源与待确认事项 | 来源、状态、缺口、不能推出什么 |

### 6.3 产品市场分析禁止项

- 不生成客户名单或推荐客户类型。
- 不判断“值不值得进入”。
- 不把 Google Trends 写成销量、GMV、进口量或真实采购需求。
- 不把平台价写成成交价、批发价、推荐报价或目标价格。
- 不把候选 HS/HTS 写成最终归类、最终税率或应缴税额。
- 不把 Made in、Production、网页产地标识写成 COO 文件或海关最终原产地裁定。
- 不猜起运港、最佳路线或承运承诺。

## 7. Slice T 静态 eval 合同

本 Slice 新增静态 eval，只检查用户可见输出，不检查底层事实是否最新。

| 检查维度 | 检查方式 |
|---|---|
| 三路线必备字段 | 每条路线必须出现本合同定义的关键字段 |
| 表格化表达 | 至少包含 Markdown 表格 |
| 内部语言不外露 | 阻断 `EvidenceCard`、`SearchLog`、`Claim`、`MatrixRow` 等 |
| 价值判断不外露 | 阻断“值得进入”“推荐客户”“最佳路线”“推荐报价”等 |
| 弱证据不升级 | 阻断搜索摘要、Google Trends、平台价、候选税号、董事/公开入口等升级断言 |
| 资料缺口可见 | 至少出现待确认、未执行、来源受限、候选或不能推出等状态词 |

## 8. 非目标

- 不联网。
- 不补真实 Google Trends、关税、法规或物流数据。
- 不生成正式客户名单。
- 不重写已有产品市场分析 graph。
- 不清理 `tmp/stage5_chillys/`。

## 9. 下一步

Slice T 完成后，后续代码 Slice 必须先说明它改善哪条路线的哪张用户可见表。若只能改善内部对象完整性，但看不到外贸用户交付收益，则继续暂缓。
